# 个性化外卖减脂系统 — 产品思路优化分析

> **你的原始思路**: 很多人点外卖，现有工具都是通用热量扫码计算，想做针对个人的定制化热量控制减脂方案
> **分析时间**: 2026-10-06
> **基于**: GitHub Top 100 减肥减脂仓库 + 全网减脂课程调研

---

## 一、你的思路核心问题诊断

### 现有方案的痛点（你发现对了）

| 现有方案 | 问题 |
|---------|------|
| 薄荷健康 / MyFitnessPal | 通用食物数据库，不区分个人体质，需要手动搜索记录 |
| FatSecret / 卡路里追踪器 | 事后记录型——吃完才知道超标，太晚了 |
| Keep / 帕梅拉课程 | 偏运动侧，不管你吃了什么外卖 |
| AI拍照识别类（cal_scanner等）| 能识别但不会推荐——告诉你"这碗面800卡"然后呢？|

### 你的差异化空间（三个关键词）

```
个性化 × 外卖场景 × 事前决策
```

**没有任何现有仓库同时覆盖这三点。** 这就是你的机会。

## 二、优化后的产品定义

### 一句话定义

> **基于个人体脂数据的 AI 外卖点餐减脂助手——告诉你该点什么、怎么搭配、吃多少。**

### 用户故事

```
小李，28岁程序员，BMI 26，体脂率 28%，每天中午外卖
→ 打开你的小程序
→ "今天想吃黄焖鸡米饭"
→ AI 回复："你的今日热量预算还剩 650kcal"
  → 推荐："黄焖鸡（鸡肉+香菇）320kcal + 半份米饭130kcal + 白灼生菜45kcal = 495kcal"
  → 替代方案："如果想吃全份米饭，把黄焖鸡换成红烧豆腐，省150kcal"
→ 小李直接照着点，热量完美达标
```

## 三、四层架构设计

### Layer 1 — 个人数据层

**目标**: 精确到个人的代谢模型

**输入数据**:
- 基础数据：身高、体重、年龄、性别
- 进阶数据：体脂率（可选，用体脂秤）、腰围、臀围
- 行为数据：每日步数、运动频率、久坐时长
- 目标数据：目标体重、减脂速度偏好（温和/标准/快速）
- 饮食偏好：过敏原、忌口、口味偏好、不吃的食材

**计算输出**:
- BMR（基础代谢率）— 用 Mifflin-St Jeor 公式
- TDEE（每日总能量消耗）= BMR × 活动系数
- 每日热量目标 = TDEE × 减脂系数（温和 0.9 / 标准 0.8 / 快速 0.7）
- 宏量营养分配：
  - 蛋白质：1.6-2.2g/kg 体重
  - 脂肪：0.8-1.0g/kg 体重
  - 碳水：剩余热量 ÷ 4

**参考仓库**:
- `srinathkumar451/Health_Tracker_App` — BMR 计算的 Streamlit 实现
- `pub-calculator-io/protein-calculator` — 个性化蛋白质需求计算
- `lizhijundev/fit_calc` — BMI/热量/减肥时间五合一计算器

### Layer 2 — AI 决策层（核心差异化）

**目标**: 在用户点外卖前，给出个性化推荐

**输入方式（三种，越用越顺）**:
1. **文字输入**: "黄焖鸡"、"沙县拌面"、"麻辣烫"
2. **截图识别**: 截取美团/饿了么菜单页 → OCR + AI 解析菜品
3. **拍照识别**: 拍外卖实物 → AI 识别菜品和份量

**AI 处理流程**:
```
用户输入菜名
→ 匹配食物数据库（中餐外卖菜品库，不是通用食材库）
→ 估算每份菜的热量/蛋白质/碳水/脂肪
→ 结合用户今日剩余热量预算
→ 生成推荐方案：
   方案A：原菜搭配 + 调整份量（如半饭/少油）
   方案B：同品类更优选择（如鸡腿肉代替五花肉）
   方案C：跨品类替代（如杂粮粥代替白米饭）
```

**关键技术**:
- 食物识别：GPT-4o Vision / Gemini Vision（参考 `maux-calories-tracker`）
- 菜单 OCR：百度 OCR / 阿里 OCR + LLM 解析
- 推荐算法：基于约束的优化（热量预算约束下最大化蛋白质）

**参考仓库**:
- `yuanxiaochenAC/MamiHealth.AI` (17★) — 饭前拍照决策，最接近你的场景
- `soda-2002/FitAgent` — AI 食物识别 + 减脂餐推荐
- `xmannii/maux-calories-tracker` (50★) — GPT-4o 食物分析，Next.js 实现
- `qwepablo12/EatWise1` (20★) — Gemini 解析自然语言食物文本
- `ignoxx/caloriemate` (40★) — 自托管 AI 卡路里追踪，隐私优先

### Layer 3 — 外卖场景层

**目标**: 深度适配外卖用户的使用习惯

**核心功能**:
1. **今日预算面板**: 一进来就看到"今天还能吃 XXX kcal"
2. **已吃记录**: 早餐 / 加餐 的快速记录（简化输入）
3. **外卖搜索**: 输入想吃的菜 → 给出推荐搭配
4. **热门外卖推荐**: 按热量效率排序的常见外卖搭配（高蛋白/低卡）
5. **「省热量」技巧**: 每道菜附上"怎么做能省 XX kcal"的实操建议

**外卖菜品数据库设计**:
```
{
  "name": "黄焖鸡米饭",
  "category": "快餐",
  "restaurant_type": "黄焖鸡",
  "default_calories": 680,
  "default_protein": 28,
  "default_carbs": 85,
  "default_fat": 22,
  "portion": "标准份",
  "variations": [
    {"name": "半份米饭", "delta_calories": -130, "delta_carbs": -33},
    {"name": "少油版", "delta_calories": -80, "delta_fat": -9},
    {"name": "加一份青菜", "delta_calories": +45, "delta_protein": +2, "delta_fiber": +3}
  ],
  "smart_swaps": [
    {"from": "全份米饭", "to": "半饭+杂粮饭", "savings": 180},
    {"from": "鸡胸肉", "to": "鸡腿肉去皮", "savings": 60}
  ]
}
```

**参考仓库**:
- `CRong941018/jianfei` (3★) — 微信小程序完整模板，热量记录+TDEE+AI拍照
- `fangge2023/ai-health-miniprogram` (13★) — AI 健康减肥微信小程序
- `Jiayu-zheng1/EveryDay_Food` (3★) — 1077 道中文菜谱热量数据库

### Layer 4 — 反馈调整层（形成数据闭环）

**目标**: 越用越准，让个性化真正"活"起来

**闭环流程**:
```
推荐方案 → 用户实际点了什么（拍照/手动记录）→ 计算偏差
→ 偏差分析：
   - 连续吃超 → 自动调整 TDEE（可能高估了活动量）或建议增加运动
   - 连续吃少 → 提醒不要过度节食（防止代谢降低）
   - 偏好某类菜 → 推荐时优先这类菜的更优搭配
→ 每周减脂报告：体重趋势 / 热量偏差 / 最常点的外卖 / AI建议调整
```

**参考仓库**:
- `yaoruiquan/CarbonCycle-FitAgent` (3★) — LangGraph AI Agent 的"计划→执行→反思→调整"闭环，最值得参考的架构
- `johnhz0229/cut_tracker` — 多用户追踪+趋势分析
- `khanhnguyendata/logweight` (11★) — 减肥数据分析

## 四、技术选型建议

### 推荐技术栈

| 模块 | 技术 | 理由 |
|------|------|------|
| 前端 | 微信小程序 (Taro/原生) | 外卖用户习惯用手机，小程序无需下载 |
| 后端 | Python FastAPI | 和 AI 模型集成方便，异步性能好 |
| AI 食物识别 | Gemini 2.5 Flash | 性价比最高，多模态能力强 |
| OCR | 百度 OCR API | 中文识别率最高 |
| 食物数据库 | 自建中餐外卖菜品库 + 薄荷 API 补充 | 通用食材库不适合外卖场景 |
| 用户数据存储 | PostgreSQL | 关系型数据 + JSON 混合存储 |
| 部署 | 先用 cloud-service 托管 | 免密钥，快速上线 |

### 成本控制策略

参考 `tahaygun/ai-calorie-tracker` (24★) 的 BYOK 模式：
- 用户自带 AI API Key → 你的服务器成本接近为零
- 免费额度：每天 3 次 AI 推荐，超出需充值或自带 Key
- 食物数据库查询不消耗 AI Token，只有图片识别才用

## 五、MVP 最小可行产品（4 周开发计划）

### Week 1 — 基础框架
- 个人数据录入 + BMR/TDEE 计算
- 每日热量预算展示
- 基础食物搜索（手动输入菜名 → 返回热量）

### Week 2 — AI 推荐核心
- 接入 Gemini Vision 做拍照识别
- 实现"输入想吃的菜 → 推荐搭配方案"功能
- 今日已摄入 vs 剩余预算实时展示

### Week 3 — 外卖场景适配
- 建立常见外卖菜品数据库（黄焖鸡、麻辣烫、沙县、盖饭、面食等 Top 50）
- 截图菜单 OCR 解析
- "省热量技巧"附加到每个推荐

### Week 4 — 闭环反馈
- 每日记录对比（推荐 vs 实际）
- 连续超标自动提醒 + TDEE 调整
- 周报生成

## 九、风险与挑战

| 风险 | 应对 |
|------|------|
| 中餐热量估算误差大（±20%）| 用区间而非精确值展示，"约450-550kcal" |
| 外卖菜品太多建不完库 | 先做 Top 50 最常见品类，AI 兜底识别 |
| 用户懒得每次记录 | 截图即记录 + 每日只记午餐（外卖主场景） |
| AI 成本 | BYOK 模式 + 缓存常见菜品识别结果 |
| 美团/饿了么自己做 | 他们做通用推荐，你做减脂垂直，更精准 |

## 总结

你的核心机会在于：**所有现有产品都在做"事后记录"，没有人做"事前决策"**。

把外卖+减脂+AI推荐三个点串起来，做一个轻量的小程序，解决的是数百万每天点外卖又想减脂的人的痛点——不是告诉他们"你吃多了"，而是在他们点之前就告诉他们"该怎么点"。

**第一步该做的**: 先建一个 50 道常见外卖菜品的数据库 + 基础 TDEE 计算器，接上 Gemini 做拍照识别，做一个微信小程序 MVP 验证需求。
